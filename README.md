## 1. Описание проекта

ИИ-система раннего прогнозирования задержек наземного городского транспорта. Backend принимает потоковую
телеметрию ТС по протоколу NDTP (TCP), накладывает её на нитку эталонного расписания и считает
производные признаки. ML-модель (CatBoost) прогнозирует отклонение от графика на целевой остановке
**за 10–15 минут** до прибытия. Система определяет вероятность опоздания и паттерн сбоя и выводит алерт
с рекомендацией и объяснением прогноза на BI-дашборд диспетчера.

```
 NDTP-терминалы / эмулятор ──TCP:9201──▶ ┌──────────── Backend (FastAPI, asyncio) ─────────────┐
 (feeder: реплей traffic.csv,             │ NDTP-парсер → состояние ТС → сопоставление          │
  ndtp-telemetry-emulator)                │ с расписанием → признаки → риск/причины/инциденты   │
                                          └──────┬──────────────────────────────┬───────────────┘
                                   HTTP /v1/predict (батч)              WebSocket /ws, REST /api
                                                 ▼                              ▼
                                  ┌──── ML-сервис ────┐              ┌── Дашборд (nginx) ──┐
                                  │ CatBoost + SHAP   │              │ карта, KPI, карточки│
                                  │ notebooks/        │              │ инцидентов, what-if │
                                  │ data_functions.py │              └─────────────────────┘
                                  └───────────────────┘
```

## 2. Стек технологий и требования

| Компонент | Технологии |
|---|---|
| Язык | Python 3.12 (все сервисы, образы `python:3.12-slim`) |
| ML | CatBoost 1.2.10 (градиентный бустинг, loss=MAE), встроенный TreeSHAP; pandas 3, numpy 2, scikit-learn |
| Backend / ML API | FastAPI, uvicorn, httpx, asyncio TCP-сервер NDTP |
| Протокол | NDTP — собственный кодек без зависимостей ([libs/ndtp/codec.py](libs/ndtp/codec.py)) |
| Дашборд | SPA (vanilla JS) + Leaflet 1.9.4, nginx 1.27 |
| Интеграции | GTFS-Realtime (protobuf), GTFS, GeoJSON; OSRM, Overpass API; подложки 2ГИС / Яндекс Карты / OSM |
| Сборка | Docker, Docker Compose v2 |
| Документация | OpenAPI/Swagger (FastAPI), Sphinx + napoleon (Google-style docstrings) |

- Состояние хранится в памяти backend: без внешних БД и брокеров, поэтому задержка минимальна, а развёртывание простое.
  Импортированные маршруты сохраняются в docker volume `routes-data`, модели — в `./models`.
- Требования: Docker Desktop / Docker Engine с Compose v2, ~4 ГБ RAM, порты 8000, 8001, 8080, 8090, 9201.
- Прогнозы и дашборд работают офлайн. Интернет используется для тайлов карты, импорта маршрутов из OSM и построения объездов.

Версии зависимостей: [backend](services/backend/requirements.txt), [ml-service](services/ml_service/requirements.txt),
[feeder](services/feeder/requirements.txt).

## 3. Быстрый старт (Quickstart)

1. Положите датасет хакатона ([Яндекс Диск](https://disk.yandex.ru/d/CA6tsj4aJJ4Aaw)) в папку `dataset/`
   рядом с этим файлом. Структура: `dataset/{train,test,validate,labels}/`, `dataset/ndtp-telemetry-emulator.tar`.
2. Соберите и запустите все модули:

```bash
docker compose up -d --build
docker compose ps          # backend, ml-service, feeder — (healthy); dashboard — Up
```

3. Откройте дашборд: **http://localhost:8080**. Поток стартует автоматически: реплей реальной телеметрии
   `dataset/validate/traffic.csv` с 07:30 МСК (утренний пик), ускорение ×10. Первые прогнозы появляются через ~8 с.

Остановка: `docker compose down`.

| Сервис | Адрес | Назначение |
|---|---|---|
| `dashboard` | http://localhost:8080 | BI-дашборд диспетчера |
| `backend` | http://localhost:8000/docs | Swagger Backend (REST, WebSocket `/ws`) |
| `backend` | `localhost:9201` (TCP) | Приём NDTP |
| `ml-service` | http://localhost:8001/docs | Swagger ML-сервиса |
| `feeder` | http://localhost:8090/docs | Управление реплеем потока |

**Основные переменные окружения** (в [docker-compose.yml](docker-compose.yml); полный список —
[services/backend/app/config.py](services/backend/app/config.py)):

## 4. Инструкция для жюри (Jury Guide)

Полная версия: **[docs/JURY_GUIDE.md](docs/JURY_GUIDE.md)**. Кратко:

- **Подача потока.** По умолчанию работает исторический датасет: `feeder` воспроизводит `dataset/validate/traffic.csv`
  как NDTP-поток. Управление — кнопки дашборда или `POST :8090/speed/30`, `/pause`, `/resume`, `/seek`.
  Штатный эмулятор:
  `docker load -i dataset/ndtp-telemetry-emulator.tar && docker compose --profile emulator up -d`.
- **Прогнозы и алерты.** Целевая остановка — первая с планом в окне **(T+10, T+15] мин**. Смотреть в панели
  «Инциденты» (прогноз опоздания, P(опоздание > 2 мин), причина, участок, план → прогноз, рекомендация, ML-факторы
  SHAP) и в карточке ТС (клик по ТС на карте). API: `GET /api/incidents`, `GET /api/vehicles/{id}`, `ws://localhost:8000/ws`.
- **Дашборд и метрики.** http://localhost:8080, без авторизации. Цвет риска зелёный / жёлтый / красный на ТС,
  участках и маршрутах. KPI «Точность онлайн (MAE)» и «Задержка обработки», панель «Производительность»,
  `GET /api/metrics`, `GET /metrics` (Prometheus).

## 6. Производительность и надёжность

Замеры: ноутбук, Docker Desktop (Windows). Сырые выводы — [scripts/out/](scripts/out/), онлайн — `GET /api/metrics`.

| Метрика | Значение |
|---|---|
| Холодный старт: backend готов / первый прогноз | 6.7 с / 7.9 с |
| ML-инференс батча живого потока (с SHAP), p50 / p95 | ≈ 39 / 46 мс |
| ML-инференс батча 1 / 50 / 200 / 1000 точек (медиана) | 29 / 20 / 47 / 82 мс (0.08 мс на точку) |
| Задержка «пакет → опубликованный прогноз», p50 / p95 | ≈ 42 / 290 мс (ориентир ТЗ — 1–2 с) |
| Цикл прогноза по всем ТС, p95; перегрузки цикла | ≈ 47 мс; 0 |
| Приём NDTP: 1000 терминалов × 5 пакетов/с | ≈ 4970 пакетов/с без потерь, обработка пакета p95 23 мкс, `/health` p50 1.5 мс |

Очередь не копится: пакеты, пришедшие за время цикла, объединяются в следующий батч, приём NDTP не ждёт ML.

| Сбой | Поведение |
|---|---|
| Обрыв связи с телематикой | Через 15 с режим «Деградация» с баннером. Часы данных идут с последним темпом, прогноз строится по последнему состоянию, при долгом обрыве — по историческим признакам. Положение ТС рассчитывается счислением пути. Сервис продолжает работать |
| Восстановление связи | Автоматически: терминал повторяет handshake, режим возвращается в online |
| Недоступен ML-сервис | Circuit breaker (3 ошибки → пауза 5 с), прогноз baseline, тег `baseline` в карточках. Возврат к ML автоматический |
| Мусор / битые кадры | Пересинхронизация по сигнатуре `0x7E7E`, соединение сохраняется |
| Перезапуск реплея | Часы данных и нитки графика пересинхронизируются |
| Медленный клиент WebSocket | Очередь из 2 снимков, память постоянна |
| Потеря связи браузера с backend | Дашборд показывает последнее состояние, опрашивает REST и переподключается к WS |
| Недоступны OSRM / Overpass | Оценка объезда по длине пути, перебор зеркал Overpass (включая российское) |

## 7. Вся реализованная дополнительная функциональность (Extra Features)

### ML

- **Качество модели:** MAE на test **61.8 с** против 93.4 с у baseline (−33.8%) ([docs/ML.md](docs/ML.md#7-метрики-качества-и-результаты-тестов)).
- **Объяснение каждого прогноза (SHAP).** Вклады 23 признаков сгруппированы в 9 паттернов поведения ТС («низкий темп»,
  «старт-стоп», «простой / долгая посадка», «время суток», «исторический профиль рейса» и др.). Разложение точное:
  `cur_dev_s + base + Σ вкладов = прогноз`. Показывается в карточках инцидента и ТС ([docs/ML.md](docs/ML.md#8-объяснение-прогнозов-shap)).
- **Дообучение из консоли.** Продолжение бустинга поверх активной модели. Активация только при улучшении MAE,
  резервная копия предыдущей модели ([docs/ML.md](docs/ML.md#9-дообучение)).
- **Оценка по трём метрикам:** score заказчика, MAE, F1 алерта «опоздание» — в сравнении с baseline и нулевым прогнозом.
- **Калиброванная вероятность опоздания:** распределение Лапласа с масштабом = валидационная MAE.
- **Паритет train/serve:** онлайн-запрос проходит через те же функции ML-ядра, что и обучение.
- **Онлайн-оценка точности** по фактическим прибытиям (KPI на дашборде).

### Приём и обработка потока

- **NDTP-кодек без зависимостей.** Handshake и `NPH_RESULT`, CRC-16/Modbus, разбор ячеек Nav00, IntSensor02, Usi08,
  Can10, Lls15, Termo16 и пропуск ячеек §6.7 по измеренным размерам. Проверен на захватах живого эмулятора.
- **Потоковый декодер** собирает кадры из произвольных TCP-фрагментов с пересинхронизацией на мусоре.
- **Map matching на нитку графика.** Геозона 45 м с проверкой отрезка трека между пакетами (момент ближайшего подхода),
  сопоставление по порядку расписания в окне [−8, +12] мин (кольцевые маршруты, встречные остановки), проекция на
  геометрию перегона по дорогам. Детектор находит 78% плановых остановок при потолке ≈ 80%, медианная ошибка времени прибытия — 7 с.
- **Часы времени данных:** корректная работа при ускорении реплея ×1…×60 и при обрыве связи.
- **Событийный цикл прогноза:** не позже 150 мс после нового пакета, батч по всем ТС.

### ETA и работа без связи

- **ETA на 8 остановок вперёд**: геометрия по дорогам, темп ТС, отстои, пробки, автобусные полосы.
  MAE 79.5 с против 100.9 с («только план») и 125.5 с («план + текущее отклонение»).
- **Счисление пути при обрыве связи:** расчётное положение ТС на карте и ETA с расширяющейся погрешностью (MAE 99.6 с при 10 мин без связи).

### What-if

9 сценариев и их комбинации:

- выпуск резерва;
- объезд по дорогам (OSRM);
- светофорный приоритет;
- купирование эффекта домино (укороченный рейс, пропуск остановок, резерв, удержание следующего ТС);
- пропуск остановок;
- поломка;
- ДТП;
- засор;
- пробки и автобусная полоса.

Результат показывает сравнение «до/после» по ТС, каскад на следующие рейсы, геометрию на карте и рекомендацию.
«Применить к живому прогнозу» инжектирует поломку, ДТП и засор в поток NDTP, и весь контур реагирует на реальное опоздание.

### Дашборд

- **Отслеживание ТС:** поиск по номеру ТС, терминала или маршрута, режим «следовать», ссылка `/#track=<unit_id>`.
- **Интерактивный таймлайн:** 6 ч истории и прогноз положения ТС на 30 мин.
- **Демо-управление потоком:** скорость ×1…×60, пауза, обрыв и восстановление.
- **Слои и панели:** сеть расписания, реальные маршруты, фильтр по риску, легенда, журнал событий, панель производительности.
- **Российские подложки:** 2ГИС и Яндекс Карты (проекция EPSG:3395), OSM; карта ограничена регионом, регионы настраиваются.
- **Светлая и тёмная тема:** статус дублируется формой маркера, контраст текста ≥ 4.5:1.

### Маршрутная сеть и интеграции

- **Геометрия 922 перегонов по дорогам** из реальных GPS-треков (OSRM map-matching), встроена в образ.
- **Реестр реальных маршрутов:** импорт из OpenStreetMap, GTFS, вручную; автопривязка ТС датасета к маршрутам OSM (8 из 12).
- **Экспорт:** GTFS-Realtime (VehiclePositions, TripUpdates с ML-прогнозом, Alerts), статический GTFS, GeoJSON;
  страница примеров для JS API Яндекса и 2ГИС — http://localhost:8080/integrations/.
- **Индекс пробок:** внешний (`PUT /api/traffic`) и живой по проездам своих ТС.

### Инженерия

- **43 автотеста:** 37 — backend и NDTP, 6 — SHAP и метрики ML.
- **Скрипты проверки:** сопоставление, ETA, онлайн-MAE, нагрузочный тест.
- **Мониторинг:** Prometheus-метрики, healthcheck-и всех контейнеров.
- **Документация генерируется из кода** (Sphinx + OpenAPI).
