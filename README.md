# Предиктор задержек городского транспорта

Система в реальном времени принимает телеметрию ТС по протоколу **NDTP**, накладывает её на нитку
эталонного расписания, с помощью ML-модели прогнозирует отклонение от графика **за 10–15 минут**
до прибытия, определяет вероятную причину сбоя и выводит алерт с рекомендациями на дашборд диспетчера.

```
 NDTP-терминалы / эмулятор ──TCP:9201──▶ ┌──────────── Backend (FastAPI, asyncio) ─────────────┐
 (feeder: реплей traffic.csv,             │ NDTP-парсер → состояние ТС → сопоставление          │
  ndtp-telemetry-emulator)                │ с расписанием → признаки → риск/причины/инциденты   │
                                          └──────┬──────────────────────────────┬───────────────┘
                                   HTTP /v1/predict (батч)              WebSocket /ws, REST /api
                                                 ▼                              ▼
                                  ┌──── ML-сервис ────┐              ┌── Дашборд (nginx) ──┐
                                  │ notebooks/        │              │ карта, KPI, карточки│
                                  │ data_functions.py │              │ инцидентов, журнал  │
                                  │ + catboost_model  │              └─────────────────────┘
                                  └───────────────────┘
```

## Запуск (одна команда)

Требуется Docker (Compose v2) и папка `dataset/` рядом с этим файлом (раздаётся отдельно, в git не хранится).

```bash
docker compose up -d --build
```

| Что | Адрес |
|---|---|
| Дашборд диспетчера | http://localhost:8080 |
| Swagger Backend | http://localhost:8000/docs |
| Swagger ML-сервиса | http://localhost:8001/docs |
| Управление реплеем (Swagger) | http://localhost:8090/docs |
| Приём NDTP (TCP) | `localhost:9201` |

Поток стартует автоматически: реплей реальной телеметрии `dataset/validate/traffic.csv` с 07:30 МСК
(утренний пик), ускорение ×10. Через ~8 с после старта на дашборде появляются прогнозы.

**Штатный эмулятор NDTP** (опционально, параллельно с реплеем):

```bash
docker load -i dataset/ndtp-telemetry-emulator.tar
docker compose --profile emulator up -d     # конфиг: scripts/emulator-config.json → backend:9201
```

Эмулятор шлёт случайную навигацию около Москвы с unitId, которых нет в расписании, поэтому его ТС
видны на карте как «без наряда» (серые). Он подтверждает совместимость парсера с протоколом, а сопоставимый
с расписанием поток даёт feeder: это тот же NDTP-клиент (handshake, пауза 200 мс, realtime-пакеты,
reconnect), но с координатами и временем из реальной телеметрии.

Остановка: `docker compose --profile emulator down`.

## Модули

| Сервис | Каталог | Роль |
|---|---|---|
| `ml-service` | `services/ml_service` | **ML-ядро: инференс и обучение.** HTTP-обёртка над `notebooks/data_functions.py` и `models/catboost_model.cbm`. ML-код не изменён: онлайн-запрос сериализуется в тот же табличный вид, что CSV датасета, и проходит через те же `load_and_preprocess_*` → `build_dataset` → `predict`. Эндпоинт `/v1/train` повторяет пайплайн ноутбука `data_work.ipynb` (выключен по умолчанию, `ML_ENABLE_TRAIN=true`). |
| `backend` | `services/backend` | **API и оркестрация.** TCP-сервер NDTP, сопоставление с расписанием, производные признаки, батч-вызовы ML, риск, причины, инциденты, деградация, метрики, REST, WebSocket. |
| `feeder` | `services/feeder` | Источник живого NDTP-потока: реплей `traffic.csv`, режимы скорости, сценарии отказов (обрыв/восстановление связи, мусор в канале) и внештатные ситуации в потоке (поломка, ДТП/засор). |
| `dashboard` | `dashboard` | BI-дашборд диспетчера (nginx, SPA на Leaflet; проксирует `/api`, `/ws`, `/feeder`). |
| `libs/ndtp` | `libs/ndtp` | NDTP-кодек без зависимостей; общий для backend и feeder. |

Backend не зависит от готовности ML-сервиса: без него он работает в деградированном режиме.

### ETA на ближайшие остановки: точность

Проверка на **test** (фактическое прибытие `time_fact_begin`), параметр затухания подобран на **train**
(`scripts/validate_eta.py`, вывод — `scripts/out/validate_eta_test.txt`):

| Режим | MAE ETA | «план + текущее отклонение» | «только план» |
|---|---|---|---|
| Связь есть | **79.5 с** (на горизонте до 2 мин — 53 с) | 125.5 с | 100.9 с |
| Нет связи 2 мин (счисление пути) | **86.1 с** | 138.0 с | 103.4 с |
| Нет связи 5 мин | **92.2 с** | 157.4 с | 104.6 с |
| Нет связи 10 мин | **99.6 с** | 171.8 с | 107.1 с |

ETA лучше обоих бейзлайнов на всех горизонтах, включая работу без связи. Оговорка: в датасете один день,
поэтому параметры (τ = 10 мин, типичное отклонение 30 с) подобраны на train; train содержит те же маршруты,
что и test, а отдельной недели для проверки нет.

### What-if: сценарии

| Сценарий | Модель воздействия |
|---|---|
| Выпуск резерва | Резерв выходит на линию через N минут и идёт по графику проблемного ТС. Пассажир уезжает первым пришедшим ТС, стоянки проблемного ТС короче, потому что пассажиры распределяются |
| Смена маршрута (объезд) | Закрытие N остановок. Объезд строится роутером по дорогам через точку в стороне от закрытого участка; добавочное время = удлинение пути / скорость. На карте — закрытый участок и линия объезда |
| Светофорное регулирование | Приоритет ОТ сокращает время перегонов впереди ТС на заданный процент |
| Купирование эффекта домино | Каскад опоздания по следующим рейсам (с поглощением на отстоях) до и после меры: укороченный рейс, пропуск остановок, резерв на следующий рейс, удержание следующего ТС |
| Пропуск остановок | Экономия времени стоянок на ближайших промежуточных остановках |
| Поломка ТС | Простой N минут. При «применить» ТС реально останавливается в потоке телематики (фидер), и всё конвейерное звено — детектор, ML, инциденты — реагирует на настоящее опоздание |
| ДТП, засор | Пропускная способность перегонов впереди падает (35% / 60%). При «применить» ТС в потоке едет медленнее |
| Пробки и автобусные полосы | Балл пробок 0–10 → множитель времени перегона. Выделенная полоса снимает 70% влияния затора. Внешний индекс пробок можно подать через `PUT /api/traffic` |

Результат: для каждого затронутого ТС ETA «до/после» по остановкам, суммарное опоздание (мин·ост.), число
остановок с опозданием > 2 мин, число следующих рейсов с опозданием, рекомендация. «Применить к живому прогнозу»
действует заданное время (время данных) и снимается автоматически или кнопкой.

Это имитационная модель поверх текущего состояния сети, а не ML: эффектов управляющих воздействий в разметке
датасета нет. Что нужно для ML-калибровки — в последнем разделе.

### Как добавлять реальные маршруты

1. **OpenStreetMap по номеру.** Во вкладке «Маршруты» ввести номер («м6», «т25», «297») → импорт всех
   направлений с именами остановок и геометрией по дорогам (PTv2). Поиск идёт сначала в административной
   границе города (`osm_area` региона), затем по всему региону. Используются зеркала Overpass, в том числе
   российское `maps.mail.ru` (`OVERPASS_URLS`).
2. **GTFS перевозчика** (zip): маршруты, направления, остановки; геометрия берётся из `shapes.txt`, а если его нет —
   строится по дорогам.
3. **Вручную:** список «название; широта; долгота» → геометрия по дорогам.
4. **Автопривязка ТС датасета:** `python scripts/link_osm_routes.py` находит маршруты OSM, проходящие по
   остановкам графика каждого ТС, и сохраняет их с привязкой в `data/routes/` (встраивается в образ).
   Результат: 8 из 12 ТС привязаны к реальным маршрутам (м86, с827, м17, 21, 577, 757, 764, 824), 93–100% остановок
   лежат на линии маршрута. Для трёх ТС уверенного совпадения нет (≤ 57%), двух не удалось проверить из-за
   недоступности Overpass. Повторный запуск дорабатывает только непривязанные ТС.

Реестр хранится в docker volume `routes-data`, поэтому импортированные маршруты переживают перезапуск.

### Геометрия маршрутов по дорогам

`python scripts/build_route_shapes.py` строит геометрию для всех 922 направленных перегонов расписания:
GPS-трек между детектированными прибытиями → OSRM `/match` (привязка к графу), иначе `/route` через точки трека,
иначе `/route` между остановками. Итог: `osrm_route_via_gps` 470, `osrm_route` 291, `osrm_match` 125, `gps` 9,
`straight` 27. Результат лежит в `data/network/shapes.json` и встраивается в образ, поэтому интернет в рантайме
не нужен. По умолчанию используется публичный демо-сервер OSRM (~1 запрос/с); для продакшена — свой OSRM на
выгрузке «Центральный ФО» (`ROUTER_URL`). Роутер нужен и для объездов в what-if, и для маршрутов, созданных вручную.

## Приём и парсинг NDTP

Реализован по `dataset/docs/Emulator-and-Telematic-Packets-Specification.md` и проверен на живом эмуляторе
(захваты трафика лежат в `libs/ndtp/tests/fixtures`).

- Кадр `NPL(15) + NPH(10) + тело`, little-endian. CRC-16/Modbus по NPH+телу, в NPL байты CRC переставлены.
- Handshake `NPH_SGC_CONN_REQUEST` и все пакеты с флагом `request` подтверждаются ответом `NPH_RESULT`.
- Ячейки: `Nav00`, `IntSensor02`, `Usi08`, `Can10`, `Lls15`, `Termo16` разбираются по полям.
  Для ячеек §6.7, бинарный layout которых в спецификации не описан, размер измерен на эмуляторе.
  Они пропускаются целиком, поэтому следующие ячейки пакета не теряются.
- Потоковый декодер собирает кадр из произвольных TCP-фрагментов. На мусоре, ложной сигнатуре `0x7E7E` или
  ошибке CRC он пересинхронизируется, не разрывая соединение (есть метрика `skipped_garbage_bytes`).
- `Nav00` → поля `traffic.csv` по таблице §8 README датасета: знаки широты/долготы из битов 5/6,
  валидность из бита 7, `peerAddress` → `unit_id` → `tr_id`.
- Отладочный `POST /api/ndtp/parse` разбирает hex-кадр прямо из Swagger (пример в Swagger — реальный кадр эмулятора).

## Сопоставление с расписанием и признаки

- **Фактическое прибытие** определяется по геозоне 45 м. Проверяется не только точка GPS, но и отрезок трека
  между точками: GPS приходит раз в 10–15 с, это 60–80 м пути, и одиночная точка часто проскакивает остановку.
  Время прибытия — момент ближайшего подхода (интерполяция).
  Сопоставление идёт по порядку расписания в окне [−8, +12] мин от плана. Так кольцевые маршруты
  (та же остановка через 20 мин) и остановки встречного направления не дают ложных срабатываний.
- **Текущее отклонение `cur_dev_s`** — отклонение на последней пройденной остановке, как в разметке.
- **Цель прогноза** — первая остановка с плановым временем в окне (T+10, T+15] мин (как в разметке).
- **Производные признаки** (на дашборде и в диагностике): средняя скорость на сегменте и плановая скорость
  сегмента, время простоя, признак «стоит на остановке / вне остановки», возраст телеметрии,
  серия сбоев GPS, тренд отклонения по последним остановкам.

## Риск, причины, инциденты

- **Уровень риска:** зелёный / жёлтый / красный. Жёлтый: прогноз опоздания > 120 с (порог `target_class=late`),
  опережение < −60 с или P ≥ 50%. Красный: прогноз ≥ 240 с, либо опоздание при P ≥ 75%. На карте цвет
  дублируется формой маркера (круг / треугольник / ромб) и подписью.
- **Вероятность опоздания** P(задержка > 120 с) — калибровка поверх точечного прогноза: ошибка регрессора
  с loss=MAE аппроксимируется распределением Лапласа с масштабом, равным MAE модели на валидации
  (ML-сервис отдаёт его из `catboost_info`).
- **Причина и паттерн** — rule-based диагностика по признакам телеметрии: простой вне остановки
  (затор/ДТП/поломка), затянувшаяся стоянка, низкая скорость на участке, нарастание отставания,
  унаследованное опоздание, опережение, потеря связи, сбой GPS, пиковая нагрузка. Каждой причине
  соответствует рекомендация диспетчеру.
- **Инцидент** — эпизод жёлтого или красного риска по ТС. Он закрывается после 2 мин (время данных)
  в зелёной зоне. Диспетчер может «принять» инцидент.

## Надёжность и деградация

| Сбой | Поведение |
|---|---|
| Обрыв связи с источником телематики | Режим «Деградация» с баннером на дашборде. Часы данных продолжают идти с последним темпом потока, прогнозы строятся по последнему известному состоянию. После 30 мин без телеметрии модель работает на исторических признаках (`telemetry_missing=1`, статистики `sched_*`). ТС помечаются «данные устарели». |
| Реконнект | Восстанавливается автоматически, никаких действий не нужно. Терминал повторяет handshake. |
| Недоступен ML-сервис | Circuit breaker (3 ошибки → пауза 5 с). Прогноз переключается на baseline «= текущее отклонение», карточки помечаются тегом `baseline`. После восстановления ML возвращается сам. |
| Мусор / битые кадры | Пересинхронизация по сигнатуре, соединение не рвётся. |
| Перезапуск реплея (время назад) | Нитка графика и часы пересинхронизируются. |
| Медленный клиент WebSocket | Очередь снимков длиной 2 (хранится только свежий снимок), память не растёт. |
| Потеря связи браузера с Backend | Дашборд показывает последнее состояние, переключается на опрос REST и переподключается к WS. |

Сценарии воспроизводятся из панели «Демо-управление потоком» на дашборде или через API фидера:
`POST :8090/outage/60`, `POST :8090/chaos/garbage`, а также `docker compose stop ml-service`.

| ML-инференс, батч 1 / 50 / 200 / 1000 точек (медиана) | 29 / 20 / 47 / **82 мс** (0.08 мс на точку) |
| Задержка «пакет → опубликованный прогноз», p50 / p95 | **~120 мс / ~470 мс** |
| Цикл прогноза (все ТС), p95 | 25–33 мс, перегрузок цикла 0 |
| Приём NDTP: 1000 терминалов × 5 пакетов/с (в сети Docker) | **~4970 пакетов/с без потерь**, обработка пакета p95 23 мкс, API p50 1.5 мс |

Задержка по телеметрии держится ниже 0.5 с при целевом ориентире 1–2 с. Очереди не копятся: пакеты,
пришедшие за время цикла, коалесцируются в следующий батч (`cycle_overruns=0`, потерь нет).
Метрики доступны онлайн: `GET /api/metrics`, `GET /metrics` (Prometheus), панель «Производительность» на дашборде.

**Качество (честная оценка онлайн-контура на `labels_test.csv`, 353 точки)** — `scripts/evaluate_online.py`

| Прогноз | MAE, с |
|---|---|
| Нулевой прогноз | 103.3 |
| Baseline `cur_dev_s` из разметки | 93.4 |
| Модель, `cur_dev_s` из разметки (офлайн-постановка) | **71.1** |
| Модель, `cur_dev_s` посчитан онлайн по GPS | **92.2** |

Детектор прибытий (`scripts/validate_matching.py`) находит 78% плановых остановок; физический потолок около 80%,
потому что в остальных местах нет GPS. Медиана ошибки времени прибытия относительно `time_fact_begin` — 7 с,
91% ошибок укладываются в 60 с.

Разница 71 → 92 с объясняется определением признака в разметке. Там `cur_dev_s` — факт на остановке
с плановым временем ≤ T, а этот факт нередко наступает **после** T. Онлайн он ещё не известен, поэтому
онлайн-контур использует последнее детектированное отклонение (вариант выбран по этой же оценке,
см. `CUR_DEV_MODE`). Онлайн-точность также считается прямо в работе, по факту прибытия на целевую
остановку: KPI «Точность онлайн» на дашборде.

## Что требуется от ML-части

ML-ядро в этой работе не менялось. Backend использует модель как есть, а перечисленное ниже закрыто
временными решениями, которые стоит заменить результатами ML-команды:

1. **Классификатор причины/паттерна сбоя.** Сейчас причина определяется rule-based диагностикой в Backend
   (`services/backend/app/risk.py`). Нужна модель (или разметка паттернов), которая по признакам
   телеметрии и расписания выдаёт тип сбоя. Её выход встраивается в `diagnose()` как ещё одна причина с весом.
2. **Вероятность отклонения.** Модель — регрессор; вероятность получается аппроксимацией Лапласа по валидационной MAE.
   Лучше отдавать откалиброванную вероятность напрямую: классификатор late/ontime/early или квантильные прогнозы
   (`loss_function=Quantile`/`MultiQuantile`). ML-сервис вернёт их полем в `/v1/predict`.
3. **Устойчивость к `cur_dev_s`, посчитанному онлайн.** Обучение на `cur_dev_s` из разметки (там есть знание
   факта после T) даёт разрыв 71 → 92 с MAE онлайн. Рекомендуется обучать и валидировать на онлайн-версии признака
   (её генерирует `scripts/validate_matching.py` → `scripts/out/online_cur_dev_*.csv`) или добавить признаки
   позиции ТС относительно остановки.
4. **Поведение без телеметрии.** При `telemetry_missing=1` модель почти полностью «списывает» текущее отклонение.
   Пример: `cur_dev_s=274` → прогноз 12 с. В режиме деградации это занижает риск. Стоит добавить в обучение
   примеры с пропуском телеметрии или ограничить дельту в этом режиме на стороне модели.
5. **Чувствительность к порядку пакетов с одинаковым `event_time`.** `speed_diff` зависит от порядка строк
   при совпадающих метках времени. Офлайн это порядок строк CSV, онлайн — порядок поступления.
   Паритет train/serve подтверждён для 351 из 353 тестовых точек, расхождения только в таких случаях.
   Стоит сделать признак детерминированным (например, агрегировать дубликаты).
6. **Масштаб:** `tr_id` — категориальный признак, поэтому для новых ТС модель опирается только на остальные
   признаки. Для сети в тысячи ТС нужен признак маршрута или участка вместо ID.
7. **ETA на ближайшие остановки (1–10 мин).** Сейчас это не ML, а кинематика + график (`services/backend/app/eta.py`),
   MAE 79.5 с. Модель ML-ядра прогнозирует только одну остановку в окне 10–15 мин. Для полного профиля нужна
   мульти-горизонтная модель (задержка на k-й остановке вперёд). Интерфейс готов: ETA-движок принимает поправки,
   а GTFS-RT TripUpdates уже подставляет ML-прогноз на целевой остановке.
8. **Калибровка what-if.** Эффекты управляющих воздействий (резерв, приоритет на светофорах, объезд, пропуск
   остановок) заданы экспертными коэффициентами. Для ML-калибровки нужна история применённых мер и их
   фактических результатов (журнал `/api/whatif/apply` можно использовать как источник такой разметки).
9. **Пробки.** Живой индекс загруженности строится по проездам наших ТС. Внешний источник (балл пробок по участкам)
   подключается через `PUT /api/traffic`; его стоит добавить и в признаки модели.
